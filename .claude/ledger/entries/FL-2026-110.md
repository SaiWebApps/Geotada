## Incident

At 09:18 PDT the committed plan ended with a fully serial pre-commit tail:
`make lint` -> `make test` (measured 5m11s) -> judge round-trip (measured ~4 min)
-> commit, targeting 09:58. Summed against measured costs this leaves under two
minutes of slack, so the ETA was arithmetically a coin flip rather than a plan.

The serialization is unforced. The judge reviews the DIFF for correctness; the
bar proves the change does not regress the suite. Neither consumes the other's
output, so nothing requires the judge to wait for green. Running them
concurrently reclaims the entire ~4 minute judge leg and converts zero slack
into a real buffer. The only true barrier is the commit, which waits on both.

The compounding risk is that a PROVE-FIRST ruling arriving AFTER a 5m11s bar run
forces a second full cycle. Firing the judge early surfaces PROVE-FIRST while
the bar is still running, so the re-prove overlaps the run instead of following it.

Related waste in the same session: a 216-line patch left unapplied in the
scratchpad (work held outside git counts as zero), and three independent tracks
(claim_dedup.py, a test fixture, content_budget.py) run in series despite
touching different files and sharing a single bar run.

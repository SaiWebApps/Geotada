Tour Algorithm · Design · v2 (corrected)
Design doc · built fresh from your algo notes

The tour generator is a narrative engine, not a router.

The bet: a great tour is a coherent, personalized story. So the route exists to serve the story — walking-efficiency is a constraint, narrative satisfaction is the product, and we make satisfaction measurable so the system tunes itself. Below: the pipeline, what's off-the-shelf, and the one piece that's actually yours to build.

Is this the best way?
Yes — narrative-first is the right architecture, and your moat.

Competitors do routing-first or fact-dumps; “the route serves the story” is the differentiated bet, and it maps cleanly onto mature libraries — so it's fast to build. Three upgrades turn it from a good idea into the best version:

Upgrade 1

Assemble, don't free-write

Your corpus is already curated beats. The story lives mostly in the ordering + light glue — not in “the LLM writes freely.” Less generation = cheaper, safer, defensible.

Upgrade 2

Beyond adjacency: give it an arc

Coherence isn't enough. Optimize for arc (open → build → payoff), must-see anchoring, and variety — a tour is a story with structure, not a coherent list.

Upgrade 3

Grade as a dev gate

Your measurability edge is real — but bake the rubric into generation and run the grader as a CI regression gate, not a per-request loop you can't afford.

The only part that's actually yours

Every box above is a library. What no library decides for you is what makes a good tour — the objective function.

Correction · 2026-06-10 · why the first build went wrong

The earlier draft said “weight the graph, run Neo4j GDS / Yen's k-shortest.” That was the mistake — and the build followed it (swapping GDS for networkx). Picking a walking tour is the Orienteering Problem — choose a budget-bounded subset that maximizes value — not shortest-path. k-shortest over a complete graph returns the trivial direct hop, and a subtractive edge_cost goes negative once the reward terms win, silently breaking Yen's/Dijkstra. You already have a working greedy orienteering selector in src/tour/selection.py. Evolve it — never replace it with a graph search.

Phase-2 objective (this is the whole game)
value = λ·lens_adjacency + μ·importance_tier + richness
choose greedily by value / walk_seconds, until the time budget is spent

Every term is ≥ 0; walk time is the cost you divide by and the budget cap — never subtracted into a signed number, so nothing ever goes negative. This is the Orienteering Problem, and src/tour/selection.py already solves it (greedy best-insertion under a budget). Your real work is tuning λ, μ against the Phase-4 grade — not writing pathfinding. Hand the user 2–3 “flavours” by re-running the same greedy with a diversity penalty on POIs already used — not from k-shortest paths.

λ lens_adjacency — selected stops match the user's lenses μ importance_tier — the must-see “gravity” (no separate field exists) / walk efficiency is the divisor + budget — never a negative term

ν·arc_fit is parked for v1 — a 5-stage arc is a whole-route property the corpus's beat tags don't cleanly support; revisit it as a cheap post-hoc reranker over the k routes, never as an edge weight.

Phase by phase

What it does · the off-the-shelf library · the one decision that matters.

Phase 01
Reach & gather
Cast a wide, cheap net: what POIs are reachable on foot in the time budget, and is the pool rich enough for a real tour? Estimate — don't build.
Off-the-shelf
Valhalla / ORS isochroneshapelyH3
The call
A real isochrone is the principled version of your cone — the true reachable polygon, anchor or no anchor (your “Take a Tour Now” has none). Gather POIs inside it; estimate sufficiency by binning into H3 hexes and summing gravity. The cone becomes a directional weight for A→B, not a hard shape.
Phase 02
Thread the story
Find a few diverse routes through the pool where the theme compounds on the user's lenses — and hand the user 2–3 “flavors” to choose from.
Off-the-shelf
reuse src/tour/selection.pygreedy orienteering
The call
Evolve the greedy selector you already have — it's a budget-bounded orienteering heuristic (best-insertion by value-per-walk-second), already golden-tested. Fold lens_adjacency into its value score so theme compounds. Get k diverse “flavours” by re-running it with a penalty on POIs already used — diversity you control directly. Not Yen's, not a complete-graph shortest-path — that's the wrong problem and it breaks on negative edge costs.
Phase 03
Compose
Turn the chosen stops + their beats into a flowing, enthralling story — corpus as the source, the model for connective tissue.
Off-the-shelf
Instructor / OutlinesDSPyAnthropic API
The call
Assemble curated beats + minimal glue rather than “write freely, no guardrails.” Use constrained generation so every sentence carries its source-beat id — that makes Phase 5 a cheap gate instead of a rewrite. And fire this once, on the route the user picks — never generate 3 narratives before the choice (that 3×'s the LLM + ~$15–20 of ElevenLabs on tours nobody takes).
Phase 04
Grade
Score the tour on satisfaction so you can iterate the algorithm scientifically — your real edge over everyone winging it.
Off-the-shelf
DeepEval · G-Evalpromptfoo
The call
An LLM-judge rubric (coherence · factual density · pacing · would-recommend) — not “compare to YouTube” (wrong medium). You have no completion-rating store yet, so today this is exemplar-calibrated against Books/ — name it that, and add ratings capture to make it real. Use it as a regression gate to catch drops; don't auto-tune λ/μ against your own judge without a held-out set + a human spot-check (that's just Goodhart).
Phase 05
Verify
Ground every claim in the corpus and cite it — adjust facts, never rewrite. Editor, not writer.
Off-the-shelf
Ragas · faithfulnessRefCheckerrapidfuzz
The call
Two different checks — don't conflate them. rapidfuzz only confirms a beat's source passage exists in its chunk (provenance), and a valid source_beat_id only proves the citation is real. Faithfulness is whether each generated sentence is actually entailed by the beat it cites — check it with a cheap entailment pass against the beat's key_claims (already in the corpus). “Editor not writer” holds only when you verify the claim, not just the citation.

Cost & latency model

Keep the spine deterministic; spend LLM dollars only when it counts.

Cheap path · every request
On-demand “Tour Now”

Phases 1–2 are deterministic graph + geometry — cents, sub-second. The walker gets one good tour immediately. No LLM in the hot path.

Pre-generate & cache the narrative for popular start points so even on-demand can serve a fully-composed tour instantly.

Full treatment · once, on the winner
Planned & curated tours

Phases 3–5 (3 LLM passes + ElevenLabs ~$15–20) run only on the route the user picks, or offline for curated city tours.

Grading (Phase 4) is a CI cost — a few hundred $/mo across thousands of eval runs — not a per-tour cost.
